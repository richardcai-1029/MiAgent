# 通用 Agent 内部架构设计说明

| 项目 | MiAgent · 通用 Agent 端侧能力底座 |
|---|---|
| 基础框架 | LangGraph 1.2.10 |
| 范围 | 上层 Agent 内部抽象，不依赖 MiClaw 具体实现 |
| 文档版本 | v1.1 |
| 对应实现 | `miagent/graph/`、`miagent/tools/`、`miagent/llm/` |

---

## 一、设计目标与核心原则

本阶段的目标是先把上层 Agent 的内部抽象冻结下来，使其不依赖 MiClaw 的具体实现。这样做的直接好处是：真实规范开放后，全部适配面集中在协议层，图、工具层、模型层无需改动。

贯穿设计的核心原则是**职责边界的严格划分**：

**交给大模型的**，是没有确定答案、需要语义理解的判断——把用户目标拆解成哪些任务、任务之间存在什么先后关系、某个任务失败后应该换成什么方案、如何把执行结果组织成给用户的回答。

**绝不交给大模型的**，是有确定答案的判断——某个任务的依赖是否已经满足、是否超出重试上限、是否所有任务都已完成、哪些任务之间没有依赖因而可以并行、任务图是否存在死锁。这些全部由确定性代码实现，集中在 `dag.py`，是无副作用的纯函数，可以穷举测试。

这条边界的实际价值在于：用模型去判断一个我们确定知道答案的问题，既慢又不可靠，而且每一次都是真实的推理开销。端侧场景下这种浪费尤其不可接受。

## 二、架构图

```
                   START
                     │
                     ▼
                  Planner            调用模型：目标 → 结构化任务图
                     │
                     ▼
                 Scheduler           确定性：依赖解析、就绪判定、完成/死锁检测
                     │
          ┌──────────┴──────────┐
          │                     │
      Local Tool            MCP Executor
     （进程内函数）              │
                                ▼
                         Mock MiClaw Server
                                │
          └──────────┬──────────┘
                     ▼
              Result Verifier       调用模型：结果算不算达成了这一步要做的事
                     │              （判定的效力由 verify.py 的纯函数把关）
                     ▼
                 Evaluator          确定性：由错误码段位与校验判定推出处置方式
              ┌──────┼───────┐
              │      │       │
           success  retry   replan
              │      │       │
              │      │       ▼
              │      │    Replanner  调用模型：终态任务结算进情景记忆，重建剩余
              │      │       │
              └──────┴───────┘
                     │
                     ▼
                 Scheduler
                     │
                all done?
                 /     \
               no       yes
               │         │
               └───      ▼
               Goal Verifier        调用模型：目标是否真的达成
                  ┌──────┴──────┐
                  ▼             ▼
              Replanner      Finalizer   调用模型：汇总为用户可读的回答
             （回到 Scheduler）    │
                                 ▼
                                END
```

图中还有一条边未在上图标出：Evaluator 在触及重试或重规划上限时判定为 `abort`，直接转向 Finalizer。有循环的图必须有强制出口，否则一次持续失败足以让任务在用户设备上无限打转。

两个校验节点问的是同一类问题：**做到的是不是要做的**。这个问题没有确定答案，因此交给模型；
而模型给出的只是判定，判定能改动什么由纯函数决定 —— 校验只能把「成功」改判为未通过，
修正过的参数必须先过工具 schema 才会被派发。校验不可用（窗口放不下、输出始终不合 schema）
时两个节点都退回原判定：少一道检查，不会凭空多出一个失败。

## 三、AgentState Schema

State 是所有节点之间唯一的通信手段。节点不互相调用，只读写它。

| 字段 | 类型 | 说明 |
|---|---|---|
| `user_request` | `str` | 用户原始目标，全程只读 |
| `history` | `list[Turn]` | 对话历史：之前各轮的摘要，由 Session 在 run 时填入 |
| `tasks` | `dict[str, Task]` | **任务图：工作记忆，只装还要调度的任务** |
| `anchor` | `Anchor` | 目标锚：用户目标与首次拆解，首次规划成功后写入，此后只读 |
| `dispatch` | `list[DispatchItem]` | Scheduler 选出的本轮待派发任务，每项自带 route |
| `outcomes` | `list[TaskOutcome]`（合并） | 本轮各分支的执行产出，Evaluator 消费后清空 |
| `reviews` | `list[Review]`（合并） | 本轮结果的语义校验判定，与 outcomes 一同被消费后清空 |
| `errors` | `list[dict]`（追加） | 失败记录，只增不改 |
| `trace` | `list[str]`（追加） | 执行轨迹，只增不改 |
| `episodes` | `list[Episode]`（追加） | 情景记忆：离开任务图的终态任务的压缩记录 |
| `verdict` | `"success" \| "retry" \| "replan" \| "abort"` | Evaluator 与完成校验的判定，路由据此分派 |
| `replan_count` | `int` | 已重规划次数 |
| `execution_count` | `int`（累加） | 累计工具调用次数 |
| `execution_summary` | `dict` | 执行概况快照 |
| `final_answer` | `str` | 给用户的回答 |
| `turn_summary` | `str` | 本轮摘要：做了什么、结论是什么，供下一轮规划参考 |
| `gap` | `str \| None` | 完成校验指出的缺口，由重规划消费，规划完即清除 |
| `unfulfilled` | `list[str]` | 规划认定没有可用工具能完成的部分，本轮不清除；非空时收尾以 `AG-1006` 结束 |
| `failure` | `str \| None` | 非空表示任务未完成，值为错误码 |

**关于字段是否使用 reducer**：LangGraph 中节点返回 `{字段: 值}` 时，默认行为是用新值替换旧值；声明了 reducer 的字段则执行合并。判断标准是该字段属于「历史」还是「当前状态」——`errors` 与 `trace` 是历史，只增不改，使用追加型 reducer；其余均为当前状态，使用替换。`tasks` 特别不使用 reducer，因为 Replanner 产出的是重建后的任务图，若采用追加会导致新旧任务混合，Scheduler 将去执行已被废弃的任务。这类问题不会报错，只会让 Agent 行为异常，属于最难定位的一类缺陷。

**关于并行带来的额外约束**：`outcomes` 与 `execution_count` 会被并行的多个执行分支同时写入，因此必须使用 reducer。若采用普通字段，各分支写回时会互相覆盖，导致只保留最后一个结果、调用计数偏低。`execution_count` 的 reducer 为累加，各分支返回增量 `1` 而非绝对值。`outcomes` 的 reducer 支持「空列表即重置」，因为 Evaluator 消费完本轮结果后需要清空，而单纯的追加型 reducer 无法表达清空。

**关于派生信息**：`tasks` 是调度状态的唯一事实来源。「哪些就绪」「是否死锁」「是否完成」一律由 `dag.py` 中的函数从 `tasks` 派生，不作为 State 字段单独存放。同一事实若存两份，任何一处漏更新都会使 Scheduler 观察到自相矛盾的状态。

**关于工作记忆与情景记忆**：任务到了终态就不再参与调度，此后它只有两个用途——重规划时告诉模型「哪条路走过了」，收尾时告诉用户「做了什么」。这两个用途都不需要完整的 Task。因此终态任务在重规划时离开 `tasks`，压缩为 `Episode`（id、描述、工具、参数指纹、成败、结果、轮次）追加进 `episodes`。`tasks` 是工作记忆，`episodes` 是情景记忆，各管一段生命周期；`execution_summary` 由 Finalizer 收尾时从两者合并得出，只有这一个写入者。不这样做的话，每一轮重规划都会带着越来越长的历史，挤占端侧本就小的窗口。

例外是仍被新任务引用的已完成任务：新任务要用 `$from` 取它们的结果，图校验也要求依赖边指向图里存在的任务，所以它们（连同其上游）留在图里。「已记录」按 id 判定，留下的任务不会在下一次结算时被重复记录。

情景记忆的去重与降级都发生在**渲染**时，不改动状态：同 (工具, 参数指纹) 只显示最新一条；本轮的记录带结果原文，更早几轮的只剩 id 与描述——那些结果在当时的重规划里已经被看过，此后模型只需知道 id 存在以便引用。每条记录另有一个去掉结果原文的简要形式：提示词放不下时逐条换上，结果最长的先换，一条结果超长只让它自己降级，其余记录的结论原样保留。实现在 `miagent/memory/`，纯函数，不 import langgraph。

这次迁移叫**结算**，由**账本**（`memory/ledger.py`）编排为三个操作：重规划前 `settle`（结算终态任务，给出可保留的已完成任务与提示词片段）、重规划后 `accept`（剪枝、判无进展、定 `failure`）、收尾时 `close`（结算剩余终态任务，给出执行概况与明细）。节点只调账本、拿结果写回；结算的步骤顺序、「记录属于刚结束的一轮而新任务属于下一轮」这类差一，都只存在于账本内部。

**关于 `failure` 的清除**：规则只有一条——成功的重规划清除它，单个任务成功不清除。前者是因为新计划按构造看到了全部失败记录并覆盖了剩余工作，恢复发生了；后者是因为重规划失败后剩余任务照常执行，它们成功不代表恢复发生。重规划侧的取值由账本的 `accept` 给出（产出新任务 → `None`；未产出 → 根因码；全是失败过的调用 → `AG-1003`），Planner / Scheduler / Evaluator 只在中止时写入，从不写 `None`。

**关于目标锚**：重规划只看到「已完成什么、失败了什么、请给出剩余任务」。几轮之后提示词里全是局部的成败记录，最初要达成什么反而只剩一句用户原话，新计划很容易越走越偏，且没有任何东西能指出它偏了。`anchor` 记录用户目标原文与首次拆解给出的各步描述——后者是模型自己对「怎样才算完成」的最初理解——在每一轮重规划的提示词里放在最前且不可裁（priority 0）。窗口连锚都放不下时抛 `AG-3001`，表示「这个任务在这个模型上放不下」，而不是把目标裁掉再让模型猜。

锚之外还有一条确定性守卫：重规划产出的新任务若**每一个**的 (工具, 参数指纹) 都在失败记录里，说明模型只是把失败过的调用原样再拆了一遍，执行只会得到同样的失败。此时判定为无进展循环（`AG-1003`），不派发。只要有一个任务是新的就不算——那一步是否再次失败由执行去回答，不猜。

**关于对话历史**：图的一次 invoke 处理一个请求；多轮对话由 `memory.Session` 承担。每次 `run` 是一轮，收尾产出的本轮摘要（`turn_summary`）连同请求、回答、错误码与执行记录存为 `Turn`；下一轮 `run` 时把历次 `Turn` 填入 `history`，Planner 将其渲染为每轮一段的提示词片段。进入提示词的是摘要而非执行历史：一两句话说明做了什么、结论是什么，规划器据此理解承接关系。

削减从最旧的一轮开始：越旧的一轮优先级数字越大、越先被削；上一轮先降为只剩结论，再往前的整段丢弃。对话历史在工具描述之前被削减——没有工具描述就无从规划，没有历史只是少了上文。轮次只在进程内保留，不落盘。保留多少轮由同一套削减规则推出，不另立数字：从最新一轮往回数，某一轮连同比它新的各轮的完整形式已超出模型的上下文上限时，它在削减中必然先于所有更新的轮次被丢弃，此后永远进不了提示词，每轮结束后即从会话中删去（`memory.session.reachable`）。最新一轮总是保留——它有紧凑形式。取模型的上下文上限而非规划器的实际预算，留下的只多不少，因此删与不删，规划器拿到的提示词逐字相同；每轮渲染后至少有固定模板那么长，保留的轮数因此不超过「上下文上限 / 模板长度 + 1」。轮次带自己的编号（第几轮），前面的轮次被删后编号不变。Replanner 不带对话历史，它有目标锚做参照。

## 四、Task Schema

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `str` | 任务唯一标识 |
| `description` | `str` | 这一步要达成什么，供 Replanner 与 Finalizer 参考 |
| `dependencies` | `list[str]` | 必须先完成的任务 id |
| `required_tool` | `str` | 要调用的工具名 |
| `arguments` | `dict` | 工具参数 |
| `status` | `TaskStatus` | 见下方生命周期 |
| `result` | `str \| None` | 执行结果 |
| `error` | `str \| None` | 失败时的错误码 |
| `retry_count` | `int` | 已尝试次数 |
| `seq` | `int` | 规划序号：模型给出这一步的先后，重规划的任务接着往后编 |

**生命周期**

```
pending ──依赖全部 done──→ ready ──派发──→ running ──┬─→ done
   │                                                └─→ failed
   └──依赖中有 failed──────────────────────────────────→ failed（级联）
```

其中级联失败一条尤为重要：若不将「依赖已失败」的任务一并标记为失败，它们会永远停留在 pending——依赖不可能再变为 done，而调度器仍认为尚有工作未完成，表现为死锁。级联需一次传播到底，下游的下游同样要标记。

**模型只填前五个字段**。`status`、`result`、`error`、`retry_count`、`seq` 属于运行时状态，由框架维护，不进入模型的输出 schema。`seq` 由模型输出的顺序决定；需要「原本的顺序」时（派发的最终决胜项、目标锚的步骤排列）一律看它而不看 `id`——`id` 是模型起的名字，按字符串排序时 `task_10` 会排在 `task_2` 之前。

## 五、Tool Schema

```
Tool
├── name                  工具唯一标识
├── description           功能描述，写给模型看
├── input_schema          JSON Schema 格式的参数结构
├── source                LOCAL / MICLAW，仅框架可见
├── required_permission   所需权限，仅框架可见
├── estimated_memory_mb   预估内存开销，仅框架可见
└── invoke()              统一入口，返回 ToolResult，永不抛异常
```

分为两类实现：`LocalTool` 包装进程内 Python 函数，参数 schema 由函数签名与 docstring 自动生成；`MiClawTool` 包装经协议调用的系统能力，schema 来自服务端的 `tools/list`。

统一抽象遵循「对模型统一、对框架分层」：面向模型时只暴露 `name`、`description`、`input_schema` 三项，不通过结构化字段传递工具来源、权限需求与资源开销；面向框架时差异完整保留，用于路由判定、超时控制与日志分层。详见《工具适配标准化开发规范》。

`invoke()` 在任何情况下都返回 `ToolResult` 而不向上抛出异常。在 Agent 的执行循环中，工具失败属于预期内的正常情形而非程序故障，模型需要看到失败原因并据此调整；若任由异常传播，整条任务链路会中断，模型失去补救机会。

## 六、LangGraph 节点设计

| 节点 | 是否调用模型 | 执行频次 | 职责 |
|---|---|---|---|
| **Planner** | 是 | 每任务 1 次 | 目标 → 结构化任务图与做不成的部分；schema 校验（含计划内部的结构）+ 并图后结构复核 |
| **Scheduler** | 否 | 每轮 1 次 | 级联失败、完成/死锁检测、就绪任务发现、路由判定、并发限流 |
| **LocalTool** | 否 | 每轮 0..N 次（并行） | 执行进程内工具 |
| **MCPExecutor** | 否 | 每轮 0..N 次（并行） | 经协议执行系统工具 |
| **ResultVerifier** | 是 | 每轮至多 1 次 | 语义校验本轮结果：是否达成该任务要做的事；参数偏差给出修正提议 |
| **GoalVerifier** | 是 | 每轮会话至多 1 次 | 对照目标锚校验整轮执行是否达成目标，未达成转重规划补做 |
| **Evaluator** | 否 | 每轮 1 次 | 逐条落库本轮结果（含校验判定），按优先级聚合出一个判定 |
| **Replanner** | 是 | 每次重规划 1 次 | 经账本结算终态任务进情景记忆，以目标锚为参照重建剩余部分，再经账本验收：只留新任务引用到的已完成任务、判无进展、定 `failure` |
| **Finalizer** | 是 | 每任务 1 次 | 经账本收账（级联失败、结算剩余终态任务、执行概况与明细），一次调用同时产出给用户的回答与本轮摘要 |

**Planner 与 Scheduler 分列两个节点**，依据是二者在执行频次（1 次对 N 次）、是否调用模型、拓扑位置（单入单出对三入三出）三方面均存在本质差异。若合并，每一轮循环都会重新进入含模型调用的节点，需要额外的守卫逻辑判断「是否首次进入」，且检查点、耗时统计与执行轨迹将混杂在一起。

**LocalTool 与 MCPExecutor 分列两个节点，但共用同一份实现**（以 `functools.partial` 绑定不同的 `source` 参数）。当前两条路径的执行体完全一致，保留分立结构的依据是二者将来会因两项确定的原因而分叉：其一，MCP 调用属 IO 密集型，批量并发可获得接近线性的收益，而本地调用受 GIL 限制并发无益（实测三次调用并发提速分别为 2.99 倍与 1.07 倍）；其二，超时机制根本不同，MCP 侧以 `select` 带超时等待数据即可，而 Python 无法安全中断一个正在执行的本地函数，只能另起子进程，代价高于收益。共用实现使得当前的分立成本近乎为零，而将来合并后再拆分则需重构图结构——在成本不对称时，应选择保留可能性的一方。

**Evaluator 不调用模型**。任务失败后应当重试还是更换方案，答案已由错误码所属段位确定：传输层错误（`MC-1xxx`）为临时故障，退避后重试多半可成；资源类错误（`MC-4xxx`）需换用更轻量的方案，重试无益；工具与权限类错误（`MC-3xxx`/`MC-5xxx`）重试无意义。这是错误码分段编码设计的最终落点。

## 六之二、并行派发

无依赖关系的任务在同一轮被一并派发。Scheduler 产出的 `dispatch` 是列表而非单项，条件边据此返回一组 `Send`，LangGraph 将其扇出为并行分支，全部完成后再汇入 Evaluator 执行一次。

同一轮内本地工具与系统工具可以同时派发到各自的节点，因为路由信息是随任务走的，而非全局状态。

**并发受配额约束。** MiClaw 侧同时在飞的调用数不得超过握手时下发的 `max_concurrent_calls`，超出者顺延至下一轮。本地工具不受此限——它们不占用系统侧资源配额，且受 GIL 约束并发本无收益。

**派发顺序：关键路径优先。** 顺序只在配额放不下全部就绪任务时起作用：排在前面的本轮派发，其余顺延。每一轮要等本轮全部结束才进入下一轮，顺延了关键路径上的任务，整张图就多跑一轮。`dag.ready()` 因此按 `(-下游最长链长度, 规划序号, id)` 排序，下游最长链只沿未终结的任务计。例：`t1`、`t2` 为叶子，`t3 → t4 → t5` 为一条链，配额 2——先派两个叶子要四轮，先派链头只要三轮。排序键全部由任务图算出，属于有确定答案的问题，不交给模型。

**并行分支看不到主状态。** `Send` 的负载即为该次节点调用所见的全部状态，因此执行节点只能返回增量（追加一条结果、调用计数加一），由 reducer 汇总。若返回绝对值，多个分支会互相覆盖。

**判定的聚合。** 一轮内可能同时产生成功与失败。Evaluator 逐条落库后，按 `abort > replan > retry > success` 的优先级聚合出单一判定——只要有任务需要重规划，整轮即转入 Replanner，它拿到的是完整任务图，能同时看到本轮成功与失败的部分。

**当前的实际收益边界。** 本地 IO 型工具可获得接近线性的提速：实测三个各等待 300ms 的任务，以链式依赖组织时总耗时 931ms，以无依赖组织时 310ms，提速 3.00 倍。MiClaw 侧的客户端已支持多个请求同时在途（见《通信规约》收发分流）：对一个能并发处理的服务端，实测三个各耗时 300ms 的调用，逐个发出总耗时约 930ms，同时发出约 305ms。实际提速取决于 MiClaw 是否并发处理；本项目的 mock 服务端逐条处理，对它没有提速。

## 六之三、任务间数据流

任务的参数若只能由模型在规划时一次写死，多个工具就只是多次互不相干的调用——
「先查电量、再按电量决定提醒内容」这类组合无法表达。参数中因此支持引用上游任务的结果：

```json
{"id": "t2", "required_tool": "system.set_alarm",
 "arguments": {"time": {"$from": "t1"}}}
```

引用在派发之前由确定性求值器替换为被引用任务的结果，执行节点拿到的是一份参数已经落实的
任务，不需要知道数据流的存在。求值与依赖解析同属调度的正确性核心，因此和 `dag.py` 一样
实现为纯函数。

两条设计约定：

**引用即依赖。** 引用了 `t1` 就自动产生对 `t1` 的依赖边，模型不必在 `dependencies` 里
再声明一遍。模型很容易写了引用却漏填依赖，那会让下游任务在上游尚未完成时被派发并取到空值，
且不报错。与其校验两处是否一致，不如让依赖从引用派生，使这种不一致在结构上不可能出现。

**只支持引用整个结果，不提供取字段的路径语法。** 需要取某个字段时用本地工具串一步
（如 `json_field`）。多一种语法就多一处要解析、要校验、要向模型解释的东西，
而这件事已有工具能做。

## 六之四、多请求并发

图内的并行派发解决的是同一请求里彼此无依赖的任务；多个用户同时发起请求，由图之上的运行时 `miagent.runtime.Runtime` 处理。每个请求仍是一次独立的 invoke，各持一份状态——一个请求中止或重规划，不影响别的请求。

```
miclaw/task.dispatch ──→ Runtime.dispatch(params)       对话标识 → 会话，协议优先级 → 运行时优先级
miclaw/conversation.end → Runtime.end(conversation)      回收该会话
                         Runtime.submit(request, session, priority) → Future[AgentState]
  ├─ 会话内串行   同一会话的请求按提交先后逐个执行
  ├─ 准入         同时在飞的请求数 ≤ max_inflight，其余排队
  ├─ 会话回收     结束通知即回收；空闲会话数 > max_idle_sessions 时回收最久没用的
  └─ 线程池执行   Session.run → graph.invoke
共享资源（SlotPool，按优先级排队的计数信号量）
  ├─ MiClaw 调用槽   容量 = budget.max_concurrent_calls
  └─ 模型推理槽     容量 = INFERENCE_SLOTS
```

`build_runtime(llm, registry, budget)` 一次装好图与两个资源槽。手工装配时漏掉任何一处都不会报错，只会让并发超出配额。

**会话内串行。** 下一轮要承接上一轮的结论（见上文对话历史），同一会话的两轮同时执行，后一轮就看不到前一轮。不同会话之间互不可见，可以并发。

**会话回收。** 每个会话各持一份轮次记录，对话标识不断出现新值时常驻内存只增不减。两条回收途径：收到 `miclaw/conversation.end` 即回收；另外空闲会话（没有请求在飞、也没有排队）超过 `max_idle_sessions` 时，回收最久没用的——系统不发结束通知时常驻内存同样有界。在飞或排队中的会话从不回收，上文不会在一轮进行中丢失。请求提交时即绑定当时的会话对象：结束通知到达前已提交的请求仍在原会话上执行完，之后同名的请求从一个新会话开始。被回收的会话再来请求时规划器少了上文，执行的正确性不受影响。`Future` 在会话状态登记完之后才交付结果，调用方拿到结果时回收已经落定。

`max_idle_sessions` 默认与 `max_inflight` 相同（10），为暂定值：尚无每个会话常驻内存的实测，先让空闲会话的常驻量与在飞请求保持同一量级，实测后按设备内存校准。单个会话保留的轮次数由模型的上下文上限推出（见对话历史）。

**配额由所有请求共用。** `max_concurrent_calls` 按会话下发，`max_concurrent_miclaw` 只约束单个请求一轮派发多少；两个请求各自按配额派发，合起来就是两倍。MiClaw 执行节点在调用期间持有共享池里的一个槽，重试的退避等待不占槽。端侧推理通常只有一个实例，模型调用经 `LLM._guarded` 同样在共享池里排队；`elapsed_ms` 从拿到槽后开始计，不含排队。

**优先级。** 协议的请求优先级（`foreground` / `background`，见《通信规约》`miclaw/task.dispatch`）映射为运行时优先级，前台先于后台。请求的优先级键为 `(-priority, 提交序号)`：排队的请求按它准入，在飞的请求争用资源槽时也按它排队——同一优先级下先提交的先拿到资源，已在执行的请求因此先于新请求完成。键由运行时设进 `contextvars`，LangGraph 派发节点时复制调用方上下文，并行分支读到的仍是发起请求的键，节点代码不需要知道自己属于哪个请求。这是一条框架语义约定，由框架契约测试固化（清单 G-11）。

**不会死锁。** 槽只在单次调用期间持有，持有期间不申请别的槽；模型调用与工具调用分在不同节点，这条天然成立。优先级反转的时长以单次调用的超时为界。

**取值。** `max_inflight` 默认 10，为项目给定的暂定值，尚无设备内存实测作依据——每个在飞请求各持一份任务图与记忆，常驻内存随它线性增长。模型推理槽默认 1：端侧推理是单个模型实例，槽数超过推理栈实际能并行服务的数目时，多出的调用在推理栈内部按到达先后排队，优先级在那里不再起作用；1 对任何推理栈都成立，推理栈确实能并行服务多路时按其实际能力调大。

**防饥饿先不做。** 严格优先级下，前台请求持续到来时后台请求可能长期等待，当前接受这一点。

**当前的实际收益边界。** 客户端已支持多个 MiClaw 调用同时在途（见六之二），能否提速取决于 MiClaw 是否并发处理。另一部分收益来自交错——一个请求等待模型推理时，另一个请求的工具调用照常执行。MiClaw 派来的请求与 Agent 反过来调用 MiClaw 工具的报文走同一条管道，由客户端的读线程分流，互不阻塞。

## 七、循环出口

图中存在三个循环：执行循环（Scheduler → 执行 → 结果校验 → Evaluator → Scheduler）、重规划循环（Evaluator → Replanner → Scheduler）、补做循环（完成校验 → Replanner → Scheduler）。有循环的图必须设置强制出口。

补做循环的出口是重规划上限：完成校验判未达成时，只在重规划次数未达上限时转 Replanner，否则带 `AG-1006` 收尾。它还受无进展判定约束 —— 补做产出的任务若全是这一轮已经调过的调用（成败都算），判 `AG-1003` 且不派发，带副作用的系统调用因此不会为了「补做」而发生第二次。

| 出口 | 触发条件 | 错误码 |
|---|---|---|
| 正常完成 | 所有任务均为 done 或 failed，重规划未交白卷，且完成校验通过 | — |
| 完成校验判未达成 | 执行跑完，但目标未达成且重规划已达上限 | `AG-1006` |
| 有做不成的部分 | 规划列出了没有可用工具能完成的部分（能力不支持、所需工具因权限不可见），能做的部分照常执行 | `AG-1006` |
| 计划规模超预算 | 单轮规划产出的待执行任务数超过累计执行预算 | `AG-1002` |
| 重规划无产出 | 重规划跑完未产出新任务，情景记忆中有失败记录 | 取根因错误码 |
| 重规划原地打转 | 新任务的 (工具, 参数指纹) 全部在情景记忆里（成败都算） | `AG-1003` |
| 单任务重试超限 | 同一任务失败次数达上限 | 转入重规划 |
| 重规划超限 | 重规划次数达上限 | `AG-1003` |
| 累计执行超限 | 工具调用总次数达上限，由 Scheduler 在派发前检查 | `AG-1002` |
| 任务图非法 | 依赖缺失、自依赖或成环，自修复后仍未改对 | `AG-1001` |
| 并图后结构非法 | 加前缀、并入保留任务后的整张图结构非法 | `AG-1004` |
| 运行期死锁 | 有未完成任务，却既无就绪也无在跑 | `AG-1005` |

结构非法的任务图在执行任何一步之前即被拦下。格式合法但结构非法的任务图若放行，会表现为调度器永远找不到可执行任务的莫名死锁，比当场报错难以定位得多。结构校验放在 schema 校验里：模型写出的依赖指向不存在的任务、依赖自身或成环时，原因与格式错误一样喂回给模型自修复，改不对才判失败；重规划时，可依赖的已完成任务一并告诉校验。`AG-1004` 是并图之后的复核，正常情况下不会触发。

没有执行任何工具的轮次不做完成校验，因此「请求里的事都做不成」要由规划说出来：计划的 `unfulfillable` 字段列出没有可用工具能完成的部分，与任务列表同一次调用给出，不多花推理。它在本轮内不清除，收尾时即使能做的都做完了也以 `AG-1006` 结束；完成校验只判能做的部分，不为一件没有工具能做的事去重规划。

关掉语义校验时（`verify=False`），重规划产出新任务不再清除 `failure`：新计划是否真的接手了失败的部分，要由完成校验在收尾前判定；没有这道判定，框架宁可把恢复成功的轮次报为未达成，也不把失败报为完成。

## 八、模型输出的可靠性

Planner、Replanner 与 Finalizer 的输出均采用 Pydantic schema 驱动，而非仅以提示词文字约束。schema 由模型定义经 `model_json_schema()` 导出后注入提示词，校验时使用同一定义——提示词中描述的格式与实际校验的格式若为两份拷贝，改动一处而遗漏另一处将导致难以察觉的不一致。

当前可用的工具名被收进 schema 的枚举字段。这带来两项收益：模型看到的 schema 直接列出合法工具名，减少幻觉；即便仍然幻觉，也会在解析阶段即被拒绝，不必白白执行一步再报工具不存在。

输出不符合 schema 时执行自修复重试：将具体的字段级校验错误反馈给模型后重新生成，而非原样重试。原样重试是以相同输入期待不同输出，仅依赖运气。

结构化输出要占用的窗口由模型层给出（`LLM.structured_reserve`）：注入的 schema 说明，加一条最长的自修复反馈。各节点拼提示词时先扣掉它，首次调用与自修复都不会超窗。上一次的原输出能放下时一并回传，让模型看到自己写了什么；放不下时只回传错误说明。

Finalizer 的 schema 是 `FinalOutput(answer, summary)`：回答给用户，摘要给下一轮规划。两者出自同一次调用，不为摘要多烧一轮端侧推理。自修复后仍不合 schema、窗口连不可裁片段都放不下、或模型不可达时，回答与摘要一并退回由执行概况生成的确定性文本——回答不能缺席，下一轮也总要有东西可参考。

上述手段属于「尽力而为」，不构成硬性保证。端侧场景下推理栈可控，可进一步引入约束解码，在采样阶段屏蔽会导致输出非法的 token，使不合 schema 的结果在物理上无法生成。同一份 schema 可直接转换为采样语法，落点已经就绪，待 MiMo 推理栈确定后接入。

需要明确的边界是：格式约束解决不了语义问题。模型仍可能选择一个存在但不适用的工具，或给出合法但错误的参数值。这类问题由 Evaluator 与 Replanner 兜底。
