# 通用 Agent 工具适配标准化开发规范

| 项目 | MiAgent · 通用 Agent 端侧能力底座 |
|---|---|
| 适用范围 | 所有接入本框架的工具，含本地工具与 MiClaw 系统工具 |
| 文档版本 | v1.0 |
| 对应实现 | `miagent/tools/` |

---

## 一、规范目标

本规范约定工具的声明、实现、错误处理与测试方式，目的是让工具作者只需关注业务逻辑本身，而把参数校验、错误分类、权限判定、资源约束等横切关注点交由框架统一承担。

这样做的直接收益是：新增一个工具的成本从"需要理解整套错误码体系与协议约定"降低为"实现一个函数并写清楚它的参数说明"；而框架层面的收益是所有工具的失败行为一致，上层的重试与降级策略无需针对单个工具做特判。

## 二、工具分类与选型原则

框架将工具分为两类，二者在抽象层面统一，在运行特性上差异显著。

**本地工具**是运行在 Agent 进程内的普通 Python 函数，调用开销为微秒级，不需要授权，不占用端侧资源配额，且通常是幂等的，可以安全重试。适用于数据解析、格式转换、日期与数值计算、任务分支判断等纯计算场景。

**MiClaw 系统工具**由系统侧提供，经 MCP 协议跨进程调用，开销为毫秒级，需要用户授权，受端侧内存配额约束，并且往往带有不可撤销的副作用。适用于系统指令调用、设备状态读取、多模态数据采集等必须由系统能力支撑的场景。

**选型原则是：凡能在本地完成的，一律实现为本地工具。** 每一次系统工具调用都意味着一次跨进程往返、一次权限判定和一份资源配额占用，在端侧场景下这些成本不可忽略。仅当能力本身必须由系统提供时，才使用系统工具。

## 三、统一抽象原则

工具层遵循一条核心原则：**对模型统一，对框架分层。**

面向大模型时，两类工具完全一致，只暴露名称、描述、参数结构三项信息。准确地说，约束的是**不通过结构化字段向模型暴露框架内部的分类维度**（如工具来源、权限需求、资源开销）——这些信息对"该不该用这个工具"的判断没有帮助，反而会被模型当作可枚举的推理维度，增加出错可能。语义层面的线索则允许传递：系统工具的 `system.` 命名前缀与 `description` 文本本身就承载了"此调用触及设备能力"的含义，这属于内容而非结构，与命名空间防重名的职能一并保留。

面向框架时，两类工具的差异被完整保留。工具来源、所需权限、预估内存开销均被记录，用于执行超时控制、权限过滤、日志分层与调用统计。信息应当提供给需要它的一方，而不是无差别地全部暴露。

## 四、工具声明规范

每个工具必须完整申报以下五项。前三项面向模型，后两项面向框架。

| 字段 | 说明 | 约束 |
|---|---|---|
| `name` | 工具唯一标识 | 全局唯一，重名视为错误 |
| `description` | 功能描述 | 写给模型看，须说明适用场景 |
| `input_schema` | 参数结构 | JSON Schema 格式 |
| `required_permission` | 所需权限 | 无需授权时显式置空 |
| `estimated_memory_mb` | 预估内存开销 | 用于端侧配额校验 |

`description` 的写法直接影响模型的调用准确率，是工具质量中最容易被低估的一环。它应当回答"什么情况下该用这个工具"，而非仅仅复述工具名。例如"按订单号查询订单状态"优于"查询订单"，因为前者同时说明了输入前提。

`required_permission` 与 `estimated_memory_mb` 由工具自行申报、由服务端统一校验。将约束写进工具声明而非散落在执行逻辑中，可以保证新增工具时不会遗漏任何一项检查。

## 五、参数与 Schema 规范

**参数结构以函数签名为唯一事实来源，禁止手写 JSON Schema。** 手写的 Schema 与函数签名构成两份彼此独立的定义，一旦参数变更而 Schema 未同步，模型将持续按旧结构传参，且这类问题不会在任何一层报错。框架提供由签名自动生成 Schema 的机制，参数类型取自类型注解，必填性由是否具有默认值决定，参数说明取自 docstring 的 `Args:` 段落。

仅当参数为嵌套结构等自动推断无法正确覆盖的情形时，才允许显式提供 Schema，并须在代码中注明原因。

参数说明应当写明格式与取值范围。模型是依据这段文字构造参数的，"起始日期，格式 YYYY-MM-DD"与"起始日期"对调用成功率的影响是显著的。

## 六、返回与错误处理规范

本节是全篇最关键的部分。工具的错误处理方式直接决定 Agent 在失败后能否自行恢复。

**第一条：工具不得向调用方抛出异常。** 在 Agent 的执行循环中，工具失败是预期内的正常情形，而非程序故障。模型需要看到失败原因并据此调整策略。若任由异常向上传播，整个任务链路会中断，模型失去补救机会。框架的 `invoke()` 已统一承担异常捕获，工具实现只需在失败时抛出携带错误码的异常，或直接让原始异常发生。

**第二条：错误必须携带错误码，细节以结构化形式承载。** 错误信息不得仅以自由文本表达。错误码决定上层的重试策略，结构化的 `detail` 字段承载机器可读的补充信息（如配额上限与实际请求值）。将细节拼进文本消息会使上层丧失程序化处理的能力。

**第三条：呈现给模型的失败信息必须包含后续行动建议。** 该文本本质上是一段提示词而非日志。仅告知"调用失败"会导致模型重复发起相同调用；应当明确指出应重试、应更换方案，还是应请求用户授权。框架依据错误码段位自动生成该建议，工具实现无需关心。

工具失败按性质分为四类，各自对应不同的错误码与处置方式：

| 失败类型 | 错误码 | 上层处置 |
|---|---|---|
| 参数不合 schema（缺失、类型不符、取值不在枚举内、多出未声明字段） | `AG-2002` | 提示模型修正参数，错误信息一次列全 |
| 执行过程抛出异常 | `AG-2004` | 提示模型修正参数或更换方案 |
| 业务性失败（调用成立但无结果） | `MC-3003` | 提示模型更换方案，重试无效 |
| 调用性失败（权限、资源、传输） | `MC-4xxx` / `MC-5xxx` / `MC-1xxx` | 按段位分别降级、请求授权或退避重试 |

**业务性失败与调用性失败必须严格区分。** 前者表示工具正常执行但业务上无结果（如查无此单），后者表示调用本身未能成立。二者若被混同，重试策略将判断错误——对前者重试是纯粹的资源浪费，对后者放弃则损失了本可成功的机会。

**参数归一化的权限边界。** 模型输出与工具声明之间存在稳定的格式漂移，框架在调用发生之前吸收其中无歧义的部分：数字写成字符串（`"3"` → `3`）、单个值漏了数组包装（`"a"` → `["a"]`）。有歧义的一律拒绝：不猜缺失的必填参数、不做模糊匹配、不静默丢弃未声明的字段。

边界如此划分是因为失败与猜错的代价不对称。格式失败会走自修复或重规划，是可控的；猜错会产生一个形式合法、语义错误的调用并被真实执行，而系统工具常带不可撤销的副作用。同理，数字不会被自动转成字符串——`63` 与 `63.0` 会得到不同的文本，该由模型明确写出它要哪一个。

## 七、权限与资源约束规范

权限与资源是两道彼此独立的关卡，任一不满足即拒绝执行。权限通过则未必资源充足，反之亦然。

权限的执行遵循"前置过滤"原则：未获授权的工具在工具列表拉取阶段即被服务端剔除，不会进入模型的可选范围。这一设计的价值在于，模型无从规划出注定失败的步骤，从而避免了一轮无效推理——在端侧场景下，每一轮推理的算力与耗电成本都是实实在在的。

资源约束的执行依赖工具申报的预估内存开销与会话建立时下发的端侧配额。超出配额的调用在执行前即被拦截，并在错误详情中同时给出配额上限与实际请求值，供上层判断是否存在可用的降级方案。

## 八、命名规范

系统工具采用 `<域>.<动词>_<对象>` 形式，如 `system.send_sms`、`system.get_battery`。域前缀承担命名空间职能，避免不同来源的工具发生名称冲突。

本地工具采用小写下划线形式，如 `add_days`、`json_field`，与普通 Python 函数命名保持一致。

工具名在注册表内全局唯一。重名不作静默覆盖处理，而是直接报错——静默覆盖会导致其中一个工具永久不可达，且极难定位。

## 九、测试要求

每个工具至少覆盖三条用例：正常调用返回预期结果、缺失必填参数返回 `AG-2002`、非法参数值不导致异常向上传播。

系统工具须额外覆盖错误码穿透测试，即验证服务端产生的错误码能够经序列化、跨进程传输、客户端还原后，在工具层保持不变，并推导出正确的重试策略。这条链路较长，任一环节丢失信息都会导致上层决策失据。

## 十、新增工具的标准流程

1. 判定工具类别。能在本地完成的实现为本地工具。
2. 实现函数本体，标注参数类型，在 docstring 中写明功能与各参数含义。
3. 本地工具使用装饰器完成包装，Schema 自动生成；系统工具在服务端声明并申报权限与内存开销。
4. 注册进工具注册表。名称冲突将在注册时报错。
5. 补齐测试用例，系统工具须包含错误码穿透测试。
6. 通过 `registry.describe()` 核对来源、权限与描述是否符合预期。

## 十一、反模式清单

以下写法在代码评审中应当被明确拒绝：

- 手写与函数签名并存的 JSON Schema
- 工具内部捕获异常后返回字符串形式的错误信息，绕过错误码体系
- 将错误细节拼接进消息文本而不使用 `detail` 字段
- 重写框架提供的 `invoke()` 方法，绕过统一的校验与兜底逻辑
- 以 `description` 复述工具名，未说明适用场景
- 把原始异常文本直接作为呈现给模型的失败信息，而不放进 `detail`
- 将业务性失败当作成功返回，或与调用性失败混同处理
- 本地可完成的计算通过系统工具实现
