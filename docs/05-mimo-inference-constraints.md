| 项目 | MiAgent · 通用 Agent 端侧能力底座 |
|---|---|
| 目标模型 | MiMo 端侧大模型 |
| 文档版本 | v1.0 |
| 状态 | MiMo 接口与推理栈当前不可获取，本文档确定约束与落点，接入后按此实现 |

---

## 一、为什么端侧模型需要单独的约束设计

第 1 周的模型层（`miagent/llm/`）已有两项保护：发出前的上下文长度检查、结构化输出的
schema 校验与自修复重试。这两项对云端模型同样适用，属于通用保护，**不构成端侧特有的约束**。

端侧模型相对云端多出三类失效模式，它们会在工具调用决策环节集中暴露：

| 特性 | 具体表现 | 对 Agent 的影响 |
|---|---|---|
| 输出稳定性弱 | 指令遵循能力弱于云端模型；同一提示词的多次输出存在差异 | 依赖模型判断的环节结果不可复现，故障难以定位 |
| 上下文窗口小 | 窗口显著小于云端模型 | 工具描述与执行历史很容易把窗口占满，正常任务也会触顶 |
| function calling 格式漂移 | 输出被 markdown 围栏包裹、参数类型漂移、工具名幻觉、JSON 截断 | 一次格式失误即导致该轮推理作废，端侧的算力与电量是实在成本 |

需要说明的是，MiMo 的具体窗口大小、推理延迟、格式遵循能力当前均不可测。
**本文档因此不写入任何具体数值**——涉及数值的地方一律做成由实现自报或由配置给定，
待真实模型接入后填入实测值。

## 二、三条硬约束

### 约束一：执行正确性不得依赖模型输出的稳定性

判据只有一句：**任何有确定答案的问题都不得交给模型**。

这一条第 1 周实际已经守住——依赖是否满足、哪些任务可并行、是否超出重试上限、
是否全部完成、是否死锁、失败该重试还是换方案，全部由 `dag.py` 与 `evaluator` 的
纯函数判定。但它此前只是实现层面的选择，没有被写成明文约束，后续加功能时很容易被破坏。

现在把它固化为两条可检查的规则：

1. 新增功能时若打算把某个判断交给模型，需先回答「这个问题有没有确定答案」。有，就不能交。
2. 模型只允许在 Planner、Replanner、Finalizer 三个节点被调用。Scheduler、执行节点、
   Evaluator 不得持有模型引用——由 `test_graph.py::test_model_is_confined_to_planning_nodes`
   以 AST 扫描强制。

第二条是第一条的可执行形式。约束若只写在文档里，等同于没有。

### 约束二：上下文超限时裁剪，而不是拒绝

当前实现在超出 `context_limit` 时直接抛 `AG-3001`。这对云端模型是合理的保守做法，
对端侧不可接受：窗口本就小，工具一多、执行历史一长，正常任务也会触顶，
拒绝即等于任务失败。

改为按预算分配、按优先级裁剪：

| 分区 | 内容 | 可否裁剪 |
|---|---|---|
| 角色与格式约束 | system 提示、输出 schema | 不可裁 |
| 当前目标 | 用户请求、首次拆解（目标锚） | 不可裁 |
| 工具描述 | 可用工具的 name / description / inputSchema | 可裁：先降为候选工具子集，再压缩 schema 描述 |
| 执行历史 | 已完成任务的结果原文 | 可裁：先摘要化，再按时间由远及近丢弃 |

裁剪顺序固定、结果确定、可单独测试；裁掉了什么必须写进 trace，否则模型基于残缺上下文
给出的错误答案将无从解释。裁到不可裁分区仍然超限时，才抛 `AG-3001`——
此时它表示的是「这个任务在这个模型上放不下」，而非「上下文管理没做」。

计量单位改为 token。MiMo tokenizer 当前不可获取，因此引入 `TokenEstimator` 接口，
默认实现按字符数近似并明确标注为近似值；真实 tokenizer 开放后替换实现，上层不变。
`context_limit` 由模型实现自报，其来源是模型本身的规格，不由本框架拟定。

### 约束三：归一化只做无歧义的修复

模型输出与工具调用之间需要一层归一化，用来吸收格式漂移。这一层的权限边界必须写死：

| 允许 | 禁止 |
|---|---|
| 去除 markdown 围栏与前后说明文字 | 用模糊匹配把不存在的工具名映射到相近的工具 |
| 补全已知的工具名命名空间前缀 | 猜测缺失的必填参数 |
| 无损类型转换（`"3"` → `3`；schema 要求数组时单值包成单元素数组） | 丢弃 schema 不认识的字段后放行 |
| 截断的 JSON 判定为失败 | 用启发式修补截断的 JSON |

理由是失败与猜错的代价不对称。**格式失败会走自修复或重规划，是可控的；猜错会产生一个
形式合法、语义错误的调用，并被真实执行。** 端侧的系统调用常带不可撤销的副作用
（发短信、改设置、下单），把模型的错误猜成一个合法调用，比让它失败危险得多。

## 三、格式漂移的四道防线

| 防线 | 手段 | 生效阶段 | 性质 |
|---|---|---|---|
| 一 | 输出 schema 收紧：工具名收进 enum，`extra="forbid"` | 生成前（提示词） | 尽力而为 |
| 二 | 归一化解析：按约束三的边界吸收无歧义漂移 | 生成后、执行前 | 尽力而为 |
| 三 | 自修复重试：把字段级校验错误喂回模型重新生成 | 解析失败后 | 尽力而为 |
| 四 | 约束解码：在采样阶段屏蔽会导致输出非法的 token | 生成中 | **唯一的保证** |

前三道都是尽力而为，代价依次递增：防线一免费，防线二是本地纯计算，
防线三要多烧一轮端侧推理。因此排序原则是能在前面挡住的绝不留到后面。

防线四是唯一能提供保证的一道，需要推理栈支持约束解码。落点已经就绪：
`schema.task_plan_model_for()` 产出的 Pydantic schema 可直接转换为采样语法，
待 MiMo 推理栈确定后接入。在此之前，`LLM.supports_native_structured_output`
标记实现是否具备原生保证，不具备则退化为前三道防线。

## 四、明确不做的事

- **不靠调高温度或多次重采样来碰运气取得合法输出。** 端侧每一轮推理都是实打实的算力与电量，
  重采样把成本转嫁给设备，且不改变输出不合法的根因。规划类调用应使用确定性采样参数。
- **不用模型去校验模型的输出。** 校验必须由 schema 与纯函数承担，否则错误只是被推迟了一层。
- **不在设计中写入 MiMo 的窗口大小、延迟、格式遵循率等数值。** 这些当前不可测，
  写进来就是自拟的假设，会被后续工作当作事实引用。
