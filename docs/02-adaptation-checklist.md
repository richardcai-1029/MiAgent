## 一、实测基线数据

以下为当前实测值，作为轻量化改造的对照基准。
环境：macOS 24.6 / Python 3.13.9 / langgraph 1.2.10。测量脚本见 `bench/baseline.py`，可复现。

| 指标 | 裸解释器 | MiAgent 协议栈 | `import langgraph.graph` |
|---|---|---|---|
| 常驻内存 RSS | 16.9 MB | **29.8 MB** | **69.8 MB** |
| 冷启动耗时 | — | 51 ms | **268 ms** |
| 加载模块数 | — | 129 个 | **852 个** |
| 其中云端/网络相关 | — | **0 个（0%）** | **333 个（39%）** |

云端模块构成：langsmith 135 · requests 68 · langgraph_sdk 42 · websockets 29 ·
urllib3 28 · httpx 22 · anyio 6 · certifi 2 · ssl 1。

MiAgent 协议栈云端模块为 0，印证了 E-1 的依赖拆分是有效的 —— 协议层、传输层、
客户端层在完全不装 langgraph 的环境下即可运行。

依赖体积（site-packages 实测）：

| 包 | 体积 | 端侧是否需要 |
|---|---|---|
| langsmith | 5.5 MB | ❌ 云端追踪服务 |
| pydantic | 3.0 MB | ✅ 协议校验必需 |
| langchain_core | 2.8 MB | 🟡 仅需其中的消息与工具抽象 |
| langgraph | 1.6 MB | ✅ 图调度核心 |
| langgraph_sdk | 0.8 MB | ❌ 面向 LangGraph Cloud |
| websockets | 0.8 MB | ❌ 云端长连接 |
| httpx / requests / urllib3 | 合计约 0.4 MB（147 模块） | ❌ 端侧走 stdio |

**结论：`langgraph.graph` 常驻 69.8 MB，已超出协议中设定的 64 MB 典型端侧配额。
框架自身即耗尽预算，裁剪为 P0 阻塞项，非优化项。**

## 二、改造清单

### A · 协议与通信适配

LangGraph 的工具调用是进程内 Python 函数调用，不存在跨进程协议、身份注册与时序约束的概念。这一整块是从零建立。

| 编号 | 差异点 | 改造方案 | 优先级 | 状态 | 落地位置 / 验证 |
|---|---|---|---|---|---|
| A-1 | 无系统级通信协议 | 建立 JSON-RPC 2.0 报文层，`result`/`error` 互斥等协议不变量由校验器强制 | P0 | ✅ | `protocol/messages.py`；`test_protocol.py` |
| A-2 | 工具调用为进程内直调，无跨进程能力 | stdio 按行分帧传输，不引入 HTTP 栈 | P0 | ✅ | `transport.py`；`test_transport.py` 含真实子进程用例 |
| A-3 | 无 Agent 身份注册语义 | 扩展 `miclaw/agent.register`，注册为「申请—批准」协商而非单向声明 | P0 | ✅ | `mock_server/server.py::_on_register` |
| A-4 | 会话无时序约束，任何时刻均可调用工具 | 握手状态机，以声明式状态表强制 `initialize → register → 调用` | P0 | ✅ | `_REQUIRED_STATE`；违规返回 MC-2002 |
| A-5 | 厂商扩展方法与标准方法无命名隔离 | 扩展方法统一 `miclaw/` 前缀，避免与未来标准 MCP 方法撞名 | P1 | ✅ | `test_protocol.py::test_extensions_are_namespaced` |
| A-6 | 无协议版本协商 | `initialize` 比对版本，不匹配返回 MC-2001 | P1 | ✅ | `test_mock_server.py::test_version_mismatch` |
| A-7 | 无心跳保活，Agent 崩溃后系统侧资源不回收 | 实现 `heartbeatIntervalMs` 上报与 `autoUnregisterAfterMs` 超时回收 | P1 | ⬜ | 协议字段已定义，实现待补 |
| A-9 | 客户端同步阻塞，并发调用需加锁串行化（id 分配非原子、管道写入可能字节交错） | 传输层多路复用：连发多个请求不等回复，靠 id 配对响应。id 配对逻辑已具备，缺「发了就走」的异步收发 | P1 | ⬜ | 图层并行已就位，此项是 MiClaw 侧实际提速的前置条件 |
| A-10 | mock 服务端为单线程循环，一次只处理一条报文 | 服务端并发处理；真实 MiClaw 行为未知，本项主要影响联调环境的保真度 | P2 | ⬜ | 与 A-9 配套 |
| A-8 | 无断线重连与会话恢复 | 传输中断后重新握手并恢复会话，或明确不支持 | P2 | ⬜ | — |

### B · 错误处理体系

LangChain 工具失败表现为 Python 异常或自由文本，无错误分类，上层无法据此做差异化决策。

| 编号 | 差异点 | 改造方案 | 优先级 | 状态 | 落地位置 / 验证 |
|---|---|---|---|---|---|
| B-1 | 错误无分层归属，无法区分底层与上层故障 | MC-/AG- 双层码；MC- 经网络回传，AG- 不出进程 | P0 | ✅ | `protocol/errors.py`；测试强制 AG-* 无整数码映射 |
| B-2 | 错误细节混在文本中，上层无法程序化处理 | 结构化 `error.data.detail`，携带机器可读字段 | P0 | ✅ | `test_client.py::test_detail_survives_the_wire` |
| B-3 | 错误码在网络两侧无法还原为同一异常 | 客户端按 `data.code` 还原为 `MiClawError`；未知码兜底不崩溃 | P0 | ✅ | `client.py::_to_exception` |
| B-4 | 无按错误类别的差异化重试策略 | 按千位段位决策：1xxx 退避重试、4xxx 延迟或降级、3xxx/5xxx 不重试 | P1 | ✅ | `protocol/errors.py::retry_policy`；`test_tools.py::TestRetryPolicyByBand` |
| B-5 | MC-2004 混合两种语义（协议未定义 / 服务端未实现） | 拆为两个码，使客户端可分别处理（前者放弃、后者降级） | P2 | ⬜ | 已识别，见 `server.py::_resolve_method` |
| B-6 | 业务失败（`isError`）与调用失败（JSON-RPC error）未在上层区分 | 上层据此选择「让模型换方案」还是「退避重试」 | P1 | ✅ | `client.py::call_tool` 将 isError 映射为 MC-3003；见 `test_business_failure_differs_from_call_failure` |

### C · 端侧资源约束

LangGraph 面向云端设计，不存在内存配额、并发上限、省电模式等概念。这是端侧相对云端多出的一整个约束维度。

| 编号 | 差异点 | 改造方案 | 优先级 | 状态 | 落地位置 / 验证 |
|---|---|---|---|---|---|
| C-1 | **框架自身常驻 69.5 MB，超出 64 MB 典型配额** | 见 E 组裁剪项；目标常驻 ≤ 45 MB | **P0** | ⬜ | `bench/` 基线已建立 |
| C-2 | 无资源配额下发机制 | 握手时下发 `ResourceBudget`，Agent 全程受其约束 | P0 | ✅ | `protocol/messages.py::ResourceBudget` |
| C-3 | 工具无资源画像，无法预判开销 | 工具申报 `estimated_memory_mb`，服务端执行前校验 | P0 | ✅ | 超配额返回 MC-4001，见 `test_memory_limit` |
| C-4 | Agent 侧无自我约束，仅依赖服务端拦截 | 客户端按 budget 预筛工具，超配额的不进模型工具列表 | P1 | ⬜ | 省一次进程往返与一轮推理 |
| C-5 | `power_saving` 已下发但无消费方 | 低电模式下降级：关闭非必要后台动作、缩短上下文 | P2 | ⬜ | 字段已定义 |
| C-6 | `max_concurrent_calls` 无执行机制 | 当前同步实现天然串行；如引入并发需加信号量，否则应移除该字段 | P2 | ✅ | `scheduler` 按 `max_concurrent_calls` 限流 MiClaw 派发，超出者顺延；本地工具受 GIL 限制不设限 |

### D · MiMo 模型接入

LangChain 的 LLM 抽象假设云端 API（HTTP 重试、流式、token 计费），与端侧模型的运行方式差异较大。

| 编号 | 差异点 | 改造方案 | 优先级 | 状态 | 落地位置 / 验证 |
|---|---|---|---|---|---|
| D-1 | LLM 抽象面向云端 API | 定义最小 LLM 接口，支持 Fake / MiMo 端侧 / 云端三种实现热切换 | **P0** | ✅ | `miagent/llm/`；模板方法统一承担上下文检查与耗时统计，Fake/云端两种实现已可切换 |
| D-2 | 端侧模型上下文窗口显著小于云端 | 上下文裁剪与摘要策略，超限抛 AG-3001 | P1 | 🟡 | 超限已在请求发出前拦截（AG-3001）；上下文裁剪与摘要策略待做 |
| D-3 | 无端云协同切换 | 端侧算力不足时路由至云端，需与省电/网络状态联动 | P2 | ⬜ | 项目背景中的「端云协同」目标 |
| D-5 | 提示词无法保证模型输出符合预期结构，一次格式失误即导致任务失败 | 计划改用 Pydantic schema 驱动：schema 由模型定义导出、与校验同源；解析失败带着具体错误自修复重试；工具名收进 enum 使幻觉在解析阶段即被拒 | **P0** | ✅ | `graph/schema.py`、`llm/base.py::complete_structured` |
| D-6 | 无法从推理栈层面保证输出合法 | 端侧推理栈可控，可上约束解码（GBNF 等），使不合 schema 的输出在采样阶段即不可能生成；同一份 schema 可直接转采样语法 | P1 | ⬜ | 落点已就绪，待 MiMo 推理栈确定 |
| D-4 | 工具描述格式与模型 function calling 格式未打通 | MCP `inputSchema` 本就是 JSON Schema，可直接喂模型，无需转换 | P1 | ✅ | `test_client.py::test_tool_schema_survives_the_wire` |

## 四、验收标准

| 项 | 标准 |
|---|---|
| 协议合规 | 报文可被标准 MCP 客户端解析；错误码整数部分符合 JSON-RPC 2.0 |
| 时序正确 | 违反 `initialize → register → 调用` 时序的调用被拒绝并返回 MC-2002 |
| 错误闭环 | 服务端抛出的每个 MC- 码，均可在客户端还原为同一 `ErrorCode` |
| 资源约束 | 超出下发配额的工具调用被拦截，`detail` 中给出实际值与上限 |
| 轻量化 | 常驻内存 ≤ 45 MB；冷启动 ≤ 150 ms；加载模块数 < 550 |
| 可测试性 | 每一层可独立测试，不依赖上层；协议规则由测试而非文档约束 |
